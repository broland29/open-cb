\subsection{AbstractClassifier}

This class provides a blueprint for classifiers. This is needed for \t{Classifier}, since this way every classifier can be wrapped in this class and switched around easily. Currently there are three classifiers supported, based on three different algorithms: K Nearest Neighbors, Support Vector Machine and Convolutional Neural Network. \t{AbstarctClassifier} specifies methods \t{train}, \t{test}, \t{classifyBoard}, \t{save} and \t{load}. These are linked to direct functionalities.


\subsection{K Nearest Neighbors}

This classifier is the simplest option a user can choose. It is based on the KNN presented in Pattern Recognition Systems. For features, it uses the color histogram, more precisely the three color histograms (blue, green, red) with a given resolution, put ``one after another''. The resolution of the histograms is given by the number of bins, which currently is set to 8. This means that the color value of one channel, ranging from 0 to 255, gets mapped into one of the eight bins, based on where it lies on the scale. The labels are from 0 to 13 or 14, depending if one specifies to unite the free classes or not, but more on this later.

Both the feature matrix and label matrix are of type \t{int}. This is good for simplicity, but also has other reasons. The class label is used directly as index in many cases. Both matrices are written to and read from the file system using simple \t{ofstream} operations. This way one can see the actual values, and there is no need to artificially convert to images, which when converted back would most probably result in loss of information.

As we know, KNN does not need actual training, it just loads the images and builds the feature matrix and label matrix from it. This happens relatively fast for the tested amount of images. Since the validation set is not used in any form, and the number of images is already low, I chose to append the validation images to the training set. As previously said, the number of classes, and hence the labels may vary. This is because I provided the option to treat classes WF and BF the same way. Both of these classes will be used as free in VAR anyways, and for KNN, the separation just brings a great amount of confusion. Since we talk about color histograms, we completely lose the notion of dimensionality. An image with bottom half black and upper half white (BF) and one like this but flipped horizontally (WF) are pretty much the same for this classifier. This can be seen in the confusion matrix if both classes are used:

The testing phase consists of running the classification on the test set, computing the confusion matrix, and from that computing the total accuracy, as well as per-class precision and recall. After getting the confusion matrix, it is enough to iterate it once: for precision (at class \t{i}) we need the sum on row \text{i}, for recall we need the sum on column \t{i}, and for accuracy we need ``everything''. As expected, the results are not at all impressive: this is a very naive approach, and the biggest drawback is the feature selected. Chess pieces are distinguished by their form, not their color.

\section{Hough}

As simple as it might seem, the implementation of the Hough line detection algorithm came with more trouble than expected. First, the signature of the base method was hard to define. After multiple changes, the current form of the method returns a vector of \t{lineRhoTheta} structures. One such structure encapsulates the two integer values describing a line (as explained in section Hough \ref{analysis:hough}), as well as two methods for easy handling of the lines: \t{drawLine} to illustrate the result, and \t{getIntersection}, since the intersection of the lines is important for us.

You may ask, why are these intersections important? Well, initially I wanted to use the Hough algorithm to detect all the lines of a chessboard, and the intersection points of these lines would have served as the corner points of the cells. In practice, perfect detection of 18 lines cannot be consistently achieved, especially with my setup. Chess boards also come in all forms and shapes, and most of them have borders (the part around the cells that are not cells, just ``decoration''), so this adds at least 4 unwanted lines in the formulae.

One assumption we can safely make is that the chessboard is square. And that it is the biggest square in the image. So, instead of looking for the lines delimiting the cells, I chose to search for the 20 most dominant lines Hough can find, compute all the intersections of all lines, and search for the points which are in the image, and closest to the corner of the image. This way we get the corner points of the chessboard. The fact that chessboard borders vary in size and often are confusing for Image Processing algorithms led me to the decision to give up finding the thickness of the border, and instead make it the user's job to fine-tune the border width parameters. This is not very elegant, but it works.
