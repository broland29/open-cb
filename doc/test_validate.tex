\chapter{Testing and Validation}
\pagestyle{fancy}

As the size of the project grew, the importance of testing and validating different modules became more and more obvious. Although not every module can and needs to be tested, certain parts of the project naturally required this seemingly extra effort. Two such parts were the classification methods and the movement validation. These will be detailed in the next sections, with a description of the used technology, metrics, and expected and actual results.

\section{Testing of Validation and Response Module}

The VAR module consists of multiple submodules, which wrap around each other ``like a cabbage''. This means that unit testing can be applied efficiently. Testing manually by playing games and writing down the found bugs is tedious and unprofessional. For a more systematic, organized testing, I used the \t{Google Test} (\t{GTest}) framework.

The \t{Google Test} framework is huge since it is designed to be versatile and suitable for commercial products. I only used a minimal subset of its functionality, mainly to keep the code simple and easy to understand. To get started with \t{Google Test}, one needs to set it up and include the \t{gtest/test.h} header. As with any other \t{C}/\t{C++} executable, the entry point will be the \t{main} function. Here we call \t{::testing::InitGoogleTest}, and end our main function with \t{return RUN\_ALL\_TESTS();}.

This way, the tests will be automatically run. I used the simplest method, \t{TEST}, which has two parameters, the test suite name and the test name. This provides us a way to define a hierarchical structuring of tests, the test suite name being the higher level one. My convention was to choose the test suite names based on the \t{C++} file they test (\t{AttackTest}, \t{MoveTest}, \t{ValidatorTest}), and define test names based on the specific thing (function or specific case) they aim to test. In the \t{CMakeLists.txt} file, tests are grouped under a separate executable. As a result, the test executable \t{Test.exe} is different from the main executable \t{OpenCB.exe} and is run independently. In Figure \ref{fig:gtest} a snippet of the console after running \t{Tests.txt} is shown.

Tests of suite \t{AttackTest} aim to test each function of \t{Attack}. Namely, these are:

\begin{itemize}
    \item \b{checkPath}: checks if different pieces can reach from one cell to another. This can be done if nothing is in their way, and their movement rule specified as x and y increments allow this. Cases tested:
    \begin{itemize}
        \item the path is free and the movement rule allows it
        \item the path is not free although the movement rule allows
        \item the path is free but the movement rule does not allow it
    \end{itemize}
    
    \item \b{canWhitePawnAttackCell}, \b{canBlackPawnAttackCell}: they check different scenarios for pawns of both colors. Cases tested:
    \begin{itemize}
        \item simple move possible
        \item double move possible
        \item diagonal capture possible
        \item simple move blocked
        \item cannot move diagonally without capturing
        \item long jump blocked
        \item moving backward
    \end{itemize}

    \item \b{canBishopAttackCell}: checks different scenarios for bishops. Cases tested:
    \begin{itemize}
        \item diagonal move possible
        \item diagonal move not possible 
        \item move not even diagonal 
    \end{itemize}

    \item \b{canKnightAttackCell}: checks the horse movement patterns in all 8 directions and some invalid scenarios. Cases tested:
    \begin{itemize}
        \item good moves
        \item cell occupied
        \item not respecting the rule
    \end{itemize}

    \item \b{canRookAttackCell}: checks different scenarios for rooks. Cases tested:
    \begin{itemize}
        \item horizontal/vertical move possible
        \item horizontal/vertical move not possible
        \item move not ever horizontal/vertical
    \end{itemize}

    \item \b{canQueenAttackCell}: checks different scenarios for queens. Cases tested:
    \begin{itemize}
        \item good moves
        \item cell occupied
        \item not respecting the rule
    \end{itemize}

    \item \b{canKingAttackCell}: checking different scenarios for kings. Cases tested:
    \begin{itemize}
        \item good moves
        \item cell occupied
        \item not respecting the rule
    \end{itemize}

    \item \b{canPieceAttackCell}: takes a real board example (\href{https://www.chess.com/article/view/best-chess-moves#kholmov}{Kholmov's Combination Against Bronstein}), picks some random pieces and calls their respective methods, checking if the output is correct.
    
    \item \b{isCellInCheck}: includes some simple tests for checking cell status. Cases tested:
    \begin{itemize}
        \item cell in check
        \item cell not in check
    \end{itemize}

    \item \b{getKingSituation}: takes some examples from the article \href{https://www.thesprucecrafts.com/check-checkmate-and-stalemate-611546}{Check, Checkmate, and Stalemate Chess Moves on thesprucecrafts.com} and puts them in tests. Cases tested:
    \begin{itemize}
        \item check case
        \item checkmate case
        \item stalemate case
        \item free case
    \end{itemize}
\end{itemize}

Rather than going through each possibility (which would be an exaggeration), there were a few specific situations selected. The examples mentioned in Section \ref{subsec:notations}. Also, this is a great place to add tests covering bugs found on the run.

    \item \b{BlackPawnCapture}: expects \t{true}, \t{"d7xc6"}, \t{"Black capture"}.

    \item \b{WhiteEnPassantFromLeft}: expects \t{true}, \t{"d5xe6ep"}, \t{"White en passant"}.

    \item \b{WhiteEnPassantFromRight}: expects \t{true}, \t{"f5xe6ep"}, \t{"White en passant"}.

    \item \b{BlackEnPassantFromLeft}: expects \t{true}, \t{"a4xb3ep"}, \t{"Black en passant"}.

\end{itemize}
\vspace{0.5cm}

The highest level of testing in VAR is done in test suite \t{ValidatorTest}. Here one can directly test the \t{Validator}. It checks for the same parameters as the tests of \t{MoveTest}, but on top of it, we can check for the correctness of \t{validator.metadata}. There are two tests implemented:

\begin{itemize}
    \item \b{BadMovementsTest}: checks for weird, outrageous cases that still could occur. Cases tested:
    \begin{itemize}
        \item no movement is made
        \item a random pawn appears in a cell that previously was free
        \item a random queen appears in a cell that previously was free, along with the previous pawn
        \item a random rook appears in a cell that previously was free, along with the previous pawn and queen
    \end{itemize}

    \item \b{KasparovVSTopalov}: takes a few steps from the beginning of the match \href{https://www.chess.com/article/view/the-best-chess-games-of-all-time#Kasparov_Topalov}{Kasparov vs. Topalov, Wijk aan Zee 1999}. Interesting checks:
    \begin{itemize}
        \item right value for \t{metadata.moveCount} after each movement
        \item right value for \t{metadata.enPassantCol} after some movements affecting it
        \item right values for \t{metadata.castle} after some movements affecting it
    \end{itemize}
\end{itemize}

\b{All the unit tests are passing.} This is crucial since unit tests are designed to check the expected functionality of VAR. If a test were to fail, it would mean that either the code is broken due to a recent change, or the test is erroneous or it became outdated. In any case, failing tests are not an option.

\section{Testing of Classification Methods}

It is common, good practice to test classification models. There are a bunch of metrics one could use, but I chose to settle with the most important ones, once again keeping things simple. Testing in this case means getting these metrics. This is done in \t{AbstractClassifier::calculateAndLogMetrics}, which requires an input parameter \t{confusionMatrix}.


% ------------------------------------- Extracting the Metrics ------------------------------------- %

\subsection{Extracting the Metrics}

A confusion matrix contains the counts of all predictions grouped based on the actual and predicted labels in a 2D matrix form. In our case, on the rows, we have actual classes, while on columns we have predicted classes. The indices range from 0 to 12 and represent classes \t{FR}, \t{WP}, \t{WB}, \t{WN}, \t{WR}, \t{WQ}, \t{WK}, \t{BP}, \t{BB}, \t{BN}, \t{BR}, \t{BQ}, \t{BK}. As long as one classifier can prepare such a confusion matrix (and each classifier is supposed to be able to do so), it can call this method.

From the confusion matrix, we extract the metrics presented in Table \ref{tab:metrics}. A clear explanation was found in the article \href{https://www.evidentlyai.com/classification-metrics/multi-class-metrics}{Accuracy, precision, and recall in multi-class classification on evidentlyai.com}.

\begin{table}[H]
    \centering
    \begin{tabular}{|l|l|l|}
    \hline
    \textbf{Metric Name} & \textbf{Formulae}                                                & \textbf{Meaning}                                                                                                                                  \\ \hline
    Accuracy             & $\frac{CorrectPredictions}{AllPredictions}$                      & \begin{tabular}[c]{@{}l@{}}Measures the proportion of correctly\\ classified cases from the total number\\ of objects in the dataset.\end{tabular} \\ \hline
    Precision            & $\frac{TP}{TP + FP}$                                             & \begin{tabular}[c]{@{}l@{}}Measures the model's ability to identify\\ instances of a particular class correctly.\\\phantom{.}\end{tabular}                      \\ \hline
    Recall               & $\frac{TP}{TP + FN}$                                             & \begin{tabular}[c]{@{}l@{}}Measures the model's ability to identify\\ all instances of a particular class.\\\phantom{.}\end{tabular}                           \\ \hline
    Macro Precision      & $\frac{\sum_{i=0}^{n-1} Precision_i}{n}$                         & \begin{tabular}[c]{@{}l@{}}Measure precision by class, then averages\\ it across classes.\\\phantom{.}\end{tabular}                                            \\ \hline
    Macro Recall         & $\frac{\sum_{i=0}^{n-1} Recall_i}{n}$                            & \begin{tabular}[c]{@{}l@{}}Measure recall by class, then averages\\ it across classes.\\\phantom{.}\end{tabular}                                               \\ \hline
    Micro Precision      & $\frac{\sum_{i=0}^{n-1} TP_i}{\sum_{i=0}^{n-1} (TP_i + FP_i)}$   & \begin{tabular}[c]{@{}l@{}}Calculate precision jointly.\\\phantom{.}\\\phantom{.}\end{tabular}                                                                                                                     \\ \hline
    Micro Recall         & $\frac{\sum_{i=0}^{n-1} TP_i}{\sum_{i=0}^{n-1} (TP_i + FN_i)}$   & \begin{tabular}[c]{@{}l@{}}Calculate recall jointly.\\\phantom{.}\\\phantom{.}\end{tabular}                                                                                                                           \\ \hline
    \end{tabular}
    \caption{Metric used for testing classification methods}
    \label{tab:metrics}
\end{table}

The \t{CorrectPedictions} parameter from Table \ref{tab:metrics} can be found by adding up the elements on the first diagonal. The \t{AllPredicitons} parameter is the sum of all elements of the confusion matrix, i.e. the size of the test set. Parameters \t{TP}, \t{FP} and \t{FN} are abbreviations of True Positive, False Positive and False Negative. A classification is counted as a True Positive (on class \t{C}) if it was predicted to belong to class \t{C} and it does belong to class \t{C}. This is equal to \t{confusionMatrix[C][C]}. A False Positive occurs when an image is predicted to be in class \t{C} but it belongs to another class. This is equal to the sum elements on column \t{C} except the element on the first diagonal. A False Negative occurs when an image is not predicted to be in class \t{C} although it belongs to class \t{C}. This is equal to the sum of elements on row \t{C} except the element on the first diagonal. Having all these we can calculate each metric as shown in table \ref{tab:metrics}.

\subsection{Importance of the Dataset and the Setup}

The idea of classifying approximately \t{47x92} pixel images (varies depending on border size) belonging to 13 classes without a huge dataset can be considered impossible. The task itself is not necessarily impossible, but it needs a big dataset. My first idea was that since the default train-validation-test split is 60-20-20, it would be nice to have at least 100 images of each class in each subset.

During the early stages of the project, I made setups of the pieces in different patterns, like putting pawns in a row, putting them diagonally, placing rooks, bishops, knights, queens, and kings in different patterns etc. This is not very natural: we can expect random positions. Although in chess not every position can be reached (for example, we cannot have two kings near each other), we need to expect incorrect setups as well, since OpenCB is designed to detect these. So true randomness is desired. We can also somewhat presume that the ratio of the pieces in the initial setup (8 pawns, 2 bishops, 2 knights, 2 rooks, 1 queen, 1 king) will be persistent over the game, and we cannot expect the users to have multiple black kings, for example.

So, as a good programmer, I wrote a script to generate random setups. It can be found under \t{misc/BoardSetupsGenerator.cpp}. It compiles to a separate executable. Its description states: \i{Generate board setups to be used for building a dataset. Continuously shuffle all pieces, take a subset of them, fill the rest with free cells, shuffle again, and print as a matrix until each piece appears INDIVIDUAL\_COUNT\_GOAL of times at least. The success criteria are checked after each iteration, where one iteration consists of generating boards having [MINIMUM\_AMOUNT, MAXIMUM\_AMOUNT] elements (non-free pieces)}. Since I wanted 100 in each subset (this means 100 in 20\%, 500 in 100\%), I set \t{INDIVIDUAL\_COUNT\_GOAL} to 500. For \t{MINIMUM\_AMOUNT} I used 10, for \t{MAXIMUM\_AMOUNT} I used 32 (all pieces). The reason for this is that the more non-free pieces are on board, the better (and the fewer images we need to take), but at the same time few-piece setups are important as well since these have a higher chance of getting cell images in which only the target piece appears (we want both ``solo'' and ``noisy'' pictures, since in practice both will occur).

Now, as the saying goes, the theory is working, the practice is what kills us. The script generated 781 setups. This is great, it contains 500 cell images of even the ``rarest'' pieces. But, setting up the board, setting up the Chess GUI, verifying the setups, pressing \t{Crop and Label}, and periodically verifying if images are indeed taken and of acceptable quality takes a lot of time. I composed a dataset of 60 board images ($60 * 64 = 3,840$ cell/labeled images) and it took me two whole days. And this is far from 781. Also, this is created for the demo setup, which tries to ensure uniform lighting, but in reality, this is hardly achievable, and not reusable for other environments (different lighting, different camera distance and angle, different chess set).

As expected, CNN performs the best, outperforming both KNN and SVM in every aspect. At the same time, the KNN and SVM metrics are unexpectedly close to each other. KNN does well in detecting free cells (compared to SVM) due to the nature of features. We can see every model struggle with black pieces, especially with black queens and kings. This was to be expected as well since images of black pieces are harder to distinguish even for the human eye.
